# CHOCOLATE QUEST

## A polished, time-based, adaptive knowledge arcade game

You are not being asked to merely redesign an old browser quiz.

You are rebuilding an existing quiz project into a polished, highly responsive, arcade-style knowledge game called **Chocolate Quest**.

The game will be used in a **CBSE school exhibition**, where visitors from different age groups should be able to walk up, understand the interface almost instantly, choose an appropriate academic difficulty level, play for a limited amount of time, and leave feeling that they interacted with a real game rather than a classroom quiz website.

The winner receives a chocolate, which is the reason for the name **Chocolate Quest**.

The experience should feel:

* premium
* playful but not childish
* minimalistic
* highly polished
* fast
* responsive
* visually satisfying
* easy to understand without instructions
* suitable for a large exhibition display
* interesting enough that someone watching another player also wants to try it

Do NOT interpret "100× better" as "add more gradients, shadows, cards, or random animations."

The improvement should come from **game design, state design, interaction design, adaptive difficulty, feedback, animation choreography, and visual polish.**

It currently contains question banks at different difficulty levels and uses a short timed quiz format with randomized questions, score tracking, restart functionality, and a victory video for a perfect result.

The existing question banks should be treated as **legacy content to import**, not discarded.

First inspect the complete project and understand:

2. Existing question-bank separation

4. Existing timer behavior
5. Existing score behavior

7. Existing celebration behavior

11. Existing bugs and brittle assumptions

For example:

```ts
type Question = {
  id: string
  prompt: string
```

# 2. CORE GAME IDEA

Chocolate Quest is primarily a **time-based score-maximization game**.

The central question is:

> "How many points can this player earn from the question bank before time runs out?"

This should be the core identity of the game.

The player should NOT simply try to complete 5 questions.

Instead:

```text
START
  ↓
Choose academic level
  ↓
Short intro
  ↓
Timed main round begins
  ↓
Answer as many questions as possible
  ↓
Correct answers generate points
  ↓
Wrong answers remove points
  ↓
Skip allows the player to move on
  ↓
Difficulty continuously adapts
  ↓
TIME EXPIRES
  ↓
3-question BOSS ROUND
  ↓
Final score calculation
  ↓
Winning/result animation
```

The exact main-round duration must be configurable rather than hard-coded throughout the application.

Create a central configuration object such as:

```ts
GAME_CONFIG = {
  mainRoundDuration: 120,
  bossQuestionDuration: 12,
  bossQuestionCount: 3,
  ...
}
```

Do not scatter magic numbers across components.

# 4. THE LIVING DIFFICULTY SYSTEM

This is one of the most important parts of the application.

Do NOT implement difficulty as:

```js
if (correct) nextDifficulty++
if (wrong) nextDifficulty--
```

That is too primitive.

The system needs to maintain an evolving estimate of the player's current performance.

Create a **Player Skill State**.

Example:

```ts
type PlayerSkillState = {
  estimatedSkill: number
  recentAccuracy: number
  recentSpeed: number
  currentStreak: number
  wrongStreak: number
  skippedCount: number
  questionsAnswered: number
  averageResponseTime: number
  confidenceTrend: number
}
```

Each question should also have an internal difficulty score from 0–100.

For example:

```text
Junior beginner        ~15–35
Junior advanced        ~35–45
Semi-senior            ~35–55
Senior                 ~50–70
B.Tech                 ~65–100
```

These numbers are examples, not rigid requirements.

---

# 5. DIFFICULTY SHOULD RESPOND TO THE PLAYER

After every answer, update the player's internal skill estimate.

Consider:

* correctness
* time taken
* question difficulty
* current streak
* recent answers
* repeated mistakes
* repeated fast correct answers
* skips
* question type performance

The next question should be chosen based on the relationship between:

```text
PLAYER SKILL
       +
QUESTION DIFFICULTY
       +
QUESTION VALUE
       +
RECENT PERFORMANCE
       +
QUESTION VARIETY
```

The player should usually receive questions near their current challenge zone.

Do not make every question harder after a correct answer.

Do not make every question easier after a wrong answer.

Instead, use a smooth adaptive curve.

The goal is for the player to feel:

> "This game somehow knows when I'm doing well."

without ever feeling:

> "The game is cheating."

# 6. QUESTION SELECTION ENGINE

Create a dedicated `QuestionSelectionEngine`.

It must consider:

* academic level
* player skill
* question difficulty
* previous questions shown
* previous question topics
* previous question types
* recent correctness
* current streak
* estimated response time
* boss eligibility
* duplicate prevention

Avoid repeatedly showing:

* the same topic
* the same mechanic
* almost identical questions
* questions the player has just answered

Use weighted selection rather than deterministic selection.

However, randomness must NEVER override obvious suitability.

The game should feel unpredictable but intelligent.

# 7. THE INTERNAL "QUESTION VALUE" SYSTEM

Every correct answer should have an imaginary internal value.

Call it something like:

**Question Value Index (QVI)**

This is not simply:

```text
Easy = 1 point
Medium = 2 points
Hard = 3 points
```

Instead, calculate the value using:

### A. Base difficulty value

Harder questions naturally have greater potential value.

### B. Time efficiency

A correct answer given quickly should generally be worth more than the same answer given slowly.

### C. Adaptive challenge bonus

A question that is meaningfully challenging relative to the player's current estimated skill should have slightly greater value.

### D. Streak bonus

A player who is answering consecutive questions correctly can gradually build a multiplier.

### E. Anti-exploit normalization

A player must not be able to farm very easy questions indefinitely for high scores.

---

# 8. EXAMPLE SCORING MODEL

Implement this as a central scoring engine rather than scattered arithmetic.

A starting model could be conceptually similar to:

```text
baseValue
× difficultyMultiplier
× speedMultiplier
× streakMultiplier
× challengeAlignmentMultiplier
```

For example:

```text
speedMultiplier:
fast answer      → high
medium answer    → normal
slow answer      → reduced
```

Do not make the exact formula visually obvious to the player.

The UI should communicate the result elegantly:

```text
+184
PERFECT
```

or

```text
+96
GOOD SPEED
```

rather than displaying mathematical internals.

The exact numerical curve should be centralized in one scoring module and easy to tune later.

---

# 9. WRONG ANSWERS

Wrong answers must produce **negative points**.

The penalty should depend on question value/difficulty but should be carefully capped so the game does not become frustrating.

A wrong answer should feel meaningful:

```text
-72
```

rather than simply:

```text
Wrong.
```

Use animated score feedback.

Do not create huge punishment spikes that make one mistake destroy an entire run.

The score may go below zero during the run if the design calls for it, but clamp behavior must be deliberate and configurable.

---

# 10. SKIP BUTTON

There must be a clearly visible **SKIP** button.

Skipping should:

* immediately move to another suitable question
* not count as a correct answer
* not award points
* naturally cost time because the player spent time deciding
* be recorded by the difficulty engine
* prevent exploitation through unlimited repeated skipping

Do not punish skipping with an arbitrary huge score penalty.

The time itself is the main cost.

Optionally introduce a very small transition cooldown so players cannot machine-gun the skip button.

---

# 11. LIVES / SHIELDS / ABILITIES

Include a lightweight ability system.

Do not let abilities overpower the actual knowledge game.

Use a small number of meaningful abilities.

Suggested default:

### SHIELD

Negates the negative-score effect of one wrong answer.

### 50/50

Removes two incorrect options on an eligible multiple-choice question.

### TIME BURST

Adds a small amount of time to the main timer.

Each should have limited availability.

For example:

```text
🛡 1
✦ 1
⏱ 1
```

The player should understand what each ability does instantly.

The abilities should feel like part of a game rather than buttons copied from a mobile game.

Do not add energy currencies, microtransactions, loot boxes, or other unnecessary systems.

4. Match / pair
5. Code or output prediction
6. "Find the incorrect statement"



Do NOT hard-code every question type directly into the main game component.

Legacy questions can initially remain MCQ.

New mechanics should be introduced using the new schema.

For Junior users, use simpler interaction mechanics.

For Senior and B.Tech users, progressively introduce more reasoning-oriented mechanics.

# 13. BOSS ROUND

The Boss Round is a major event.

It must contain **exactly 3 questions**.

The main timer stops when the main round ends.

Then the interface should visually transition into a distinct boss state.

Example:

```text
──────────────
   BOSS ROUND
──────────────

3 QUESTIONS
NO SECOND CHANCES
```

Do not literally use a cartoon monster unless it fits the final art direction.

The "boss" can instead be represented through:

* darker visual treatment
* stronger typography
* subtle lighting
* special sound cue
* stronger animation
* unique background treatment
* higher score stakes

The three questions should be selected from the difficult end of the player's available academic level.

However, they should still be calibrated against the player's actual performance.

Do not simply give Junior players B.Tech questions.

Boss questions should feel difficult **for that player**.

Each boss question can use a different mechanic.

For example:

```text
Boss Q1 → difficult MCQ
Boss Q2 → reasoning/code question
Boss Q3 → final challenge
```

Give boss answers significantly higher value than standard questions.

Wrong answers should have stronger consequences, but not absurd penalties.

Create a dedicated:

```ts
BossEngine
```

rather than mixing boss behavior into the regular game loop.

# 16. ANIMATION PHILOSOPHY

Animations are extremely important.

But they must be:

**smooth + short + intentional**

not noisy.

Prefer:

* 180–450 ms transitions for most interactions
* subtle spring motion
* fade/scale
* controlled slide transitions
* score number transitions
* soft particles
* subtle glow changes
* timer pulse only when appropriate

The game should never feel sluggish.

Do not animate every element simultaneously.

Animation hierarchy should be:

```text
PLAYER ACTION
      ↓
IMMEDIATE RESPONSE
      ↓
SCORE FEEDBACK
      ↓
QUESTION TRANSITION
```

Use CSS transforms/opacity where possible for performance.

Avoid expensive continuous animations that can make the exhibition machine stutter.

# 18. ANSWER FEEDBACK

Correct answer:

* selected answer reacts
* incorrect options become visually secondary if necessary
* positive score burst
* subtle particles
* score counter animates
* streak indicator updates
* next question transitions smoothly

Wrong answer:

* selected answer reacts clearly
* negative score animation
* subtle red/warm feedback
* correct answer may be revealed depending on game mode
* next question follows without browser alerts

TIMEOUT:

* different feedback from wrong answer
* timer visibly reaches zero
* question closes
* no confusing reuse of the wrong-answer event

The current legacy project uses browser `alert()` for these events. Remove this completely from the new experience.

# 32. FAIRNESS AND ANTI-EXPLOIT DESIGN

The game must prevent obvious score exploits.

Examples:

* repeating easy questions
* skipping forever
* double-clicking answers
* pressing two answers almost simultaneously
* triggering answer callbacks twice
* timer race conditions
* score being awarded twice
* abilities being activated twice
* going backward into already answered questions
* boss questions accidentally being counted twice

Every question should have a single-resolution state:

```text
UNANSWERED
ANSWERING
RESOLVED
```

Once resolved, additional clicks must do nothing.
